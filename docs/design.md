# 实现说明

## INI 自动补全

构建时用 Windows SDK 的资源编译器将 `config/CohabitationGateExperiment.ini` 原样嵌入 ASI，作为唯一默认配置来源。确认五项游戏条件定位兼容后、读取设置及初始化管理窗口前，`EnsureConfigDefaults` 补齐缺失项；启动器或无关子进程不执行此写入。仅启动时补全，后续五秒循环仍负责重新读取已有配置。

按原生 INI 的分区及键名语义忽略大小写，只向第一个同名分区插入缺少的键，缺少整个分区则追加完整默认分区。已有值（含空值、无效值及 0）、注释、未知项和名字不改写，重复运行无新增项时不写磁盘。新增键默认附带对应说明；旧 ANSI 文件仅追加 ASCII 键值，避免新中文注释迫使原文件转码。UTF-8、UTF-8 BOM、UTF-16LE 和系统 ANSI 均保留原编码；UTF-8 BOM 紧贴首分区时只插入换行，使 Win32 Profile API 能读取首分区。

输出先写入同目录临时文件并刷新，重新核对原文件未变化后原子替换；只读、共享冲突、不可识别数据或外部修改会停止补全，清理临时文件并保留原配置。文件不存在时创建内置默认 INI。日志区分新增键/分区数量与失败错误码，失败后仍使用原配置及既有读取兜底。

## 弹窗中英文切换（v0.1.3）

共享 `UiLanguage` 模块提供语言枚举、集中维护的双语文案键和 INI 读写接口。`[UI] Language` 支持 `zh-CN` / `en-US`，缺失或未知值回退中文；值不区分大小写。与伴侣偏好和名字共用原有 INI，只写入 ASCII 语言值，保留其他分区、名字和注释。读取和保存通过同一锁串行化，只有保存成功才发布新语言。

两个原生对话框注册语言变更消息，主动切换时同步刷新当前窗口，异步通知其他窗口；销毁时解除注册。插件原有五秒配置循环重新读取语言，因此手动编辑 INI 也会通知窗口。刷新只更新静态文案、动态提示及名字后缀，并保留选中项和列表顶部位置。状态提示记录文案键，重新翻译时保留其语义；名字框不参与语言刷新，保留草稿及编辑选区。

美容窗口只重建显示列表，不提交选中对象；确认和取消仍走原有返回路径。下拉框获得焦点时拦截默认确认按钮，避免 Enter 同时保存名字或进入编辑器。布局增加顶部语言栏，并将居中位置限制在当前显示器工作区。角色名仅在原生名字不可读取时翻译“伴侣 N”备用标签，不改变真实原名或自定义名字。

## F8 伴侣管理（v0.1.3）

管理窗口复用美容窗口已核对的当前玩家路径和真实已婚记录列表。插件线程每 50 ms 检查配置的管理热键（默认 F8），并通过私有注册窗口消息把操作派发到游戏窗口线程；窗口的按键消息也捕获短按。配置仍每 5 秒重新读取。窗口只在游戏前台且总开关开启时响应，模态窗口不重复创建。

管理热键使用同一 INI 的 `[UI] ManagerHotkey`，缺失或无效时默认 F8。`PartnerHotkey` 模块解析单键及 Ctrl / Alt / Shift 组合，将键码和修饰键作为一个原子值发布；窗口消息和工作线程轮询共用同一匹配逻辑。每五秒重新读取配置，切换绑定时轮询先同步当前按下状态，避免因重绑定把已按住的键当作新按下。管理窗口标题从当前热键生成，热键刷新消息只更新标题，不重建输入或提交草稿。该模块不写用户配置。

当前操控实体与关系数据所属的主玩家必须分别读取。切换德米安后，操控实体有自己的角色编号，但没有 contents 组件；关系组件仍在主玩家上。定位器从原生美容同时调用的两个 getter 恢复 manager 主玩家字段及 session 操控实体字段，交叉核对 world 和 manager。运行时从主玩家读取关系组件并核对 owner，从操控实体读取角色编号，返回前再次核对两个对象未改变；不以主玩家的角色编号代替当前角色。由此没有伴侣的主角可读取有效空列表，而不会显示另一位主角的伴侣。

游戏启动或切换显示模式时可能重建主窗口，旧入口也可能不再转发销毁通知。轮询独立核对缓存句柄是否仍有效、属于当前进程且可见，失效时重新查找并绑定实际窗口。每个窗口用独立属性保存前任窗口函数；仍在其他插件调用链中的旧窗口保留自己的转发入口，延迟销毁通知只清理匹配的绑定，避免清除新窗口的状态。绑定、F8 接收和管理窗口打开均有诊断日志。

选择优先伴侣以单次 INI 写入保存 `PreferredPartnerKey`，成功后原子更新现有路由。写入和配置重新加载共用锁，避免已读取的旧配置覆盖用户刚保存的选择；没有真实已婚记录的键仍无法制造新的关系。窗口每秒和每次操作前核对角色、组件、可操作角色编号及关系集合，失效后要求重新打开。

名字统一使用现有 `CohabitationGateExperiment.ini` 的 `[PartnerNames]` 分区，按可操作角色、NPC 保存键和角色模板三元组区分。值用 UTF-16 十六进制编码，只写入 ASCII，保留中文、引号、等号和分号，避免 INI 语法改变名字，同时保留现有 INI 的编码和注释。校验 1～30 个 UTF-16 单位及完整代理对，拒绝空白名、控制字符和非法编码。重置只删除对应覆盖，不影响其他配置，美容选择列表同步使用此覆盖。

客户端名字入口从 `TrocTrChangeCharacterNameAck` RTTI 及其处理方法恢复：核对状态组件路径、UTF-16 字符串赋值 ABI，以及客户端完整 ActorId 注册表查找链。不使用固定 RVA。更新显示名时逐个核对关系记录的实例编号、客户端注册表、NPC 保存键和角色模板，再在游戏窗口线程调用原生字符串赋值函数，保留引擎的分配和引用计数。

读取原名时同时处理已缓存长度和长度为 `MAXDWORD` 的原生 UTF-16 字符串。后者表示尚未缓存长度，需要按终止符读取，最多 256 个单位；不能直接当成超长字符串跳过，否则只会更新插件列表，实际角色仍保留原名。此检查不修改原生字符串的长度缓存。

名字仅更新客户端状态组件的显示名，不更新服务端 NPC 保存数据。每秒重新检查已婚实例，为读档或新召唤的实例应用保存的覆盖；不跨场景直接写缓存地址。重置、离婚、角色切换或总开关关闭时，对仍可核对的实例还原改名前的名字；原版已经自行更名且不再等于插件覆盖值时保留原版的新值。对象销毁后丢弃实例跟踪，不再解引用旧地址。该三元组不是存档槽标识，相同编号的存档共享覆盖。

## 管理窗口召唤所选伴侣

窗口第三个操作按钮为“召唤所选伴侣”。点击时核对当前角色与关系集合，结束模态窗口；窗口销毁并恢复游戏输入后，再调用原生客户端召唤请求发送函数。没有从窗口线程调用服务端控制器，也不使用客户端关系组件修复服务端实例。该操作只受总开关和自身入口兼容性控制，不依赖婚姻提交覆盖或全员召唤开关。

原版请求只带一字节召唤标志和四字节可操作角色保存键，没有 NPC 保存键。插件为窗口选中的 NPC 保存键、模板、角色和所属玩家建立一次性关联，使用已核验原始字节读写器支持的高位标志作为短期请求令牌，在服务端对应业务派发入口恢复规范的 1 后继续原版流程。普通 0/1 请求保持原样。一次只允许一条窗口请求，十秒到期，令牌六十秒内不复用；未知、迟到、玩家不符的令牌不回退到默认伴侣。

服务端收到请求后，再只读核对当前客户端实体、完整 ActorId、角色编号和关系组件身份，避免排队期间切换角色或读档。原生派发函数继续负责玩家和角色保存键检查。在同一次服务端调用中，临时选人作用域只允许目标玩家、当前角色、真实状态 2 保存键和模板对应的对象；使用原有 `ReconcilePartnerAction`、原版控制器、创建复用及原生回执。实际需要新建实例时，使用原版同行创建分支（第六参数为 true），由游戏选择当前操控角色附近的位置，保留其场景与创建检查；原版房屋分支使用住处出场点。已有实例继续复用，不写坐标或强制传送。全局偏好不改变，窗口请求不扩展到所有伴侣，也不改写保存的同行标志。

定位由请求 RTTI、其描述符中的包编号、原生伴侣查询调用关系、序列化字段宽度、原始字节读写器、参数传递和服务端召唤控制器共同确认。服务端业务函数包含多个 chained unwind 区段，通过 x64 unwind 的父函数信息确认它们属于同一入口。定位或独立挂钩失败只禁用召唤按钮，保留已有关系挂钩和管理功能。日志 `PARTNER MANAGER SUMMON` 区分发送、上下文取消、未进入控制器及原生结果，注册表核验不替代画面和跟随验证。

## 条件覆盖

原版部分恋爱入口包含：

```text
CheckTribe(Human) && CheckFriendlyLevel(<Me>)>=2 && IsMarriageable() && !HasLivingTogether()
```

当前分别挂钩以下条件类型的评估入口：

| 类型 | 配置键 | 有效结果覆盖 |
| --- | --- | --- |
| pa::ConditionData_CheckFriendlyLevel | IgnoreFriendlyLevel | 按虚拟等级 127 重算比较 |
| pa::ConditionData_IsMarriageable | IgnoreMarriageable | 1 → 0 |
| pa::ConditionData_HasLivingTogether | IgnoreLivingTogether | 仅取反语境下 0 → 1；正向检查保持原结果 |
| pa::ConditionData_CheckAffinityLevel | IgnoreAffinityLevel | 按虚拟等级 127 重算比较 |
| pa::ConditionData_CheckTribe | IgnoreTribe | 1 → 0 |

引擎三态返回为 0=条件满足、1=不满足、2=上下文不可用。每个包装函数都先调用原函数，再根据总开关及子开关覆盖有效真/假结果；2 和未知值原样返回。此处没有增加好感或直接写入婚姻数据。

v0.1.3 的美容修复保留条件评估器第三参数。已核对原生 NOT 节点对该参数 `xor 1`，AND 继续传递；仅在参数为 1 时覆盖同居条件，避免隐藏需要“已有伴侣”的美容入口。游戏内已验证该配置下美容恢复。

CheckFriendlyLevel 和 CheckAffinityLevel 支持等于、不等于、大小比较等多种运算。子开关覆盖对应类型的结果，不只覆盖婚姻入口的 >=2 / >=3；CheckTribe 子开关也不限于 Human 参数。其他任务中的这些条件同样可能受影响。开关不改变好感、亲密度或角色种族，剧情与 Single/Dating/Married 阶段控制仍保留。

### 等级覆盖必须保持成功与失败互斥

已提取的交互数据中，Affinity_Start_Success 使用好感 >=2，Affinity_Start_Fail 使用好感 <2；Propose_Success / Propose_Shop 使用亲密度 >=3，Propose_Fail / Propose_Shop_Fail 使用亲密度 <3。它们分别是独立的正向比较条件，不是共用一个比较结果后再统一取反。

旧实现将等级条件的“不满足”统一改成“满足”，因此可能同时放行“>=3 成功”和“<3 拒绝”。当前实现按同一个虚拟等级 127 重新求值，使这两个比较保持互斥。实际等级不变，原结果为 2 或未知值时也不重算。

自动定位器会解析等级评估器的运算字段读取、六分支 switch 表和阈值字段读取，再从各分支的 setcc / 布尔取反指令恢复比较语义。当前两个类型的字段偏移均解析为 0x1a（运算）、0x1b（阈值），六个编号分别对应 ==、!=、<=、>=、<、>；这些值没有硬编码进覆盖函数。解析失败时拒绝安装挂钩。

虚拟值 127 是当前有符号单字节等级字段可表达的最高值，不是实际游戏等级上限。它可以影响其他非婚姻等级分支，例如“等级恰好等于 3”将不成立，因此仍需考虑全局条件覆盖的影响。

### 示爱与求婚是不同流程

Affinity_Start 与 Propose 在交互表中各有成功和失败记录，且所用等级类型及关系阶段条件不同。普通求婚成功/失败记录都包含参数值为 1 的 CheckMaritalState；示爱记录还含参数值为 0、2 的关系阶段判断。这里只确认它们不是同一交互或同一关系阶段检查，没有把所有阶段条件统一移除。

已触发拒绝对话、好感降低，说明玩家进入了失败结果，但不能仅凭此确定所有底层限制都已满足。修正比较方向不等于直接写入交往或婚姻状态。

当前 CheckTribe 实现的匹配路径返回 0，不匹配或未能解析出有效对象的路径返回 1，没有独立的返回 2 分支。因此启用种族覆盖后，这两种返回 1 的情况都会被覆盖，无法仅凭返回值区分。其他类型若返回 2，则仍原样保留。

## 自动定位流程

实现位于 ConditionTarget.cpp，不依赖节名称或固定游戏 RVA：

1. 检查宿主是可读的 PE64 模块，按节属性和 VirtualQuery 枚举可读范围；跳过未提交、不可读和保护页。
2. 搜索完整的 MSVC 修饰类型名，从名称前的两个 64 位字段回溯 TypeDescriptor。
3. 搜索 x64 Complete Object Locator，检查 signature=1、主对象偏移为 0、self 指回自身、类型 RVA 以及类层次结构的首个基类引用。
4. 查找指向 Locator 的绝对指针，将紧随其后的指针数组视为候选虚表；只接受指向宿主可执行区的入口。
5. 在候选虚表各入口中识别条件分派函数，从条件对象自身虚表的间接尾跳转中读取评估槽偏移，除以指针大小得到实际槽号。不固定分派槽或评估槽。
6. 使用 PE x64 异常目录确定评估函数边界，再检查上下文读取、不可用返回和对应的布尔结果转换模式。
7. 对两个等级类型，再从函数中恢复比较字段、六分支跳转表及每个分支的比较运算。
8. 要求每个条件只有一个兼容候选。全部五个条件定位完成后才进入挂钩安装阶段。

分派指令支持已识别的 disp8 / disp32 间接跳转，以及可选的 REX.W 前缀。忽略相对调用地址、上下文字段偏移、栈布局和跳转距离等构建细节；保留结构与返回结果模式检查。

这些检查只是兼容性依据，不能证明未来版本的业务语义必然不变。编译器改变指令生成模式时也可能拒绝定位，需要人工适配。

## 挂钩与配置线程

- 原函数指针在包装函数发布前全部保存。
- 安装时覆盖位掩码保持 0，包装函数暂时返回原版结果。
- 用 VirtualProtect 临时开放写权限，用 InterlockedCompareExchangePointer 比较并替换虚函数槽，再恢复内存保护。
- 如果某个槽安装失败，尝试撤回之前已经安装的槽，且不启用任何覆盖。其他插件修改过的槽不会被强行覆盖。
- 工作线程每 5 秒读取总开关和五个子开关，用一个原子位掩码发布当前启用条件，避免回调读取半更新的内存状态。
- 日志包含 PID、每个条件解析得到的 RVA 和槽号，以及加载 / 开关状态。不包含每次调用的计数或运行时自检。

发布 INI 的功能开关均设为 1，PreferredPartnerKey=0。启动时先补齐缺失配置；补全失败或运行中删键时，解析器仍保留关闭兜底：总开关关闭，只有同居子开关缺省为 1。源码与 INI 注释为中文，构建使用 /utf-8。

五项条件覆盖只替换虚函数表入口。新增的提交资格挂钩使用 MinHook 修改进程内的函数入口并建立原函数跳板，不修改磁盘 EXE、资源包或存档格式。应完整退出游戏后再更新或卸载 DLL，不支持运行中卸载。

## 婚姻提交资格覆盖

配置为 [Relationships] / IgnoreExistingMarriageOnCommit，发布 INI 设为 1，缺键兜底为 0；总开关 Enabled=0 时也不执行覆盖。原生保护入口必须成套兼容并安装，不能强行把资格失败改成成功。

### 已确认的路径

当前 EXE 中，RVA 0x019229c0 的资格函数先扫描当前可操作角色的关系数组，发现状态 2 就返回 false；随后检查目标在各个可操作角色下的关系。RVA 0x02b451b0 的更新路径调用该函数，失败时在写入前退出；通过后还会检查目标记录，才写入 NPC 保存数据和运行时关系数组的状态 2。这些地址仅是分析记录，不是源码中的固定定位常量。

### 自动恢复布局与只读兼容检查

定位器在可执行区搜索“检查状态 2、拒绝、按记录步长继续扫描”的循环，再用异常目录取得函数范围，交叉检查二维数组读取、目标关系检查、成功/失败布尔返回。当前自动恢复结果为：组件数组偏移 0x290，外层数组 16 字节一项，内层记录步长 0x38，状态偏移 0xe，可操作角色标识偏移 0xa。

私有组件只复制原函数允许读取的前缀，因此还使用 HDE64 逐条验证该函数族：this 保存到 RSI，组件读取只涉及 owner、关系数组及数组计数；拒绝未知字段访问、this 指针转存、入口已有跳转挂钩等变体。该检查会使部分未来代码变体不兼容，但可避免在不确定布局上构造伪组件。

### 私有视图重新检查

1. 先调用完整的原资格函数；本来允许时直接返回 true。
2. 原版拒绝且开关启用时，通过 ReadProcessMemory 复制当前组件前缀及关系数组，限制计数、容量和总快照长度；失败时保留原版 false。
3. 仅在副本中，把属于当前可操作角色的状态 2 记录转换为该检查会跳过的值 3。其他角色的记录原样保留，真实组件和 NPC 数据不写入。
4. 用私有组件视图再次调用原函数。目标已是当前角色伴侣时，其副本状态 3 会进入原版的目标排除分支；目标属于其他角色时，状态 2 仍会被原版拒绝。
5. 只有原函数重新检查通过才返回 true；随后由调用者继续执行原版婚姻状态更新。

这不是直接写入第二位配偶，也不会伪造成功消息。后续提交代码仍可能失败。原版“取第一个对象”的公共查询现已接入下面的目标路由，完整伴侣列表 UI 没有新增。

MinHook 只在安装时更改函数入口；运行中切换配置使用原子布尔开关，不反复写机器码。日志区分 COMMIT RESOLVED、COMMIT HOOK INSTALLED、请求开关及 CommitOverrideActive。首次私有视图被原函数接受时输出 COMMIT RECHECK；它只证明资格重新检查通过，不证明状态提交成功。

## 当前婚姻对象路由

原公共查询在每个可操作角色的记录数组中返回第一个状态不是 3 的对象。首次与 A 结婚后，即使 B 的状态已更新，继续使用首对象也可能让场景和其他流程选回 A。当前增加只读路由，不删除或重排真实关系记录。

自动恢复的信息包括：

- 从 HasLivingTogether 评估器的相对调用中定位公共查询，检查其 TLS / 数组访问与首对象循环；当前 RVA 为 0x01922910。
- 查找调用提交资格检查、并同时包含保存数据状态 2 写入和运行时记录构造的唯一写入函数；当前为 0x02b451b0，资格调用返回点为 0x02b45239。
- 从资格函数恢复 NPC 参数到保存记录键的读取链；当前偏移依次为 0x68、0x20、0x28、0x28。没有固定函数 RVA 或字段常量。

资格包装函数通过调用返回地址区分写入路径和预检。只有写入路径接受时才记住 NPC 的保存记录键，不借用或保存 NPC 对象指针。原生事务与场景可能使用不同组件，因此偏好按可操作角色保存；选择时再次在调用组件的真实缓存中验证所有权和已婚状态。

普通公共查询包装函数先调用原函数。原结果不可用、路由关闭、无偏好，或目标未在缓存中唯一对应到当前角色的状态 2 记录时，原样返回。验证通过时返回真实缓存内的目标记录地址。v0.1.1 的离婚调用单独使用真实目标记录的只读快照，原因见后面的删除换位保护；不会凭空创建已婚记录。

PreferredPartnerKey=0 使用本进程中实际写入路径记录的目标；非 0 可以指定一个已经属于当前角色的已婚记录键，且优先于自动偏好。该值仍受 Enabled 和 IgnoreExistingMarriageOnCommit 控制，不用于制造未婚对象。自动偏好不持久化，关闭提交覆盖会清空它。

v0.1.1 将提交、公共查询、创建、出场、两条离婚入口和三种交互请求处理方法，共 9 个 MinHook 入口共同创建、排队启用；定位或安装不完整时撤回这一组，五项条件覆盖可继续运行。运行中只切换开关和键值。条件虚表已被挂钩后，定位显式使用先前保存的 HasLivingTogether 原评估器。

普通路由仍可用于场景和展示；离婚查询根据已定位的调用返回地址单独分流，不接受全局展示偏好。完整多人列表 UI 未新增。日志区分预检、写入资格、真实缓存选择和回退，不把资格接受当作持久化成功。

## 同居 / 召唤全员扩展

SpawnAllPartners 在发布 INI 中设为 1，缺键兜底为 0，受总开关控制，但不要求同时启用婚姻提交覆盖。它扩展下一次原版出场 / 收回调用；v0.1.2 还扩展原版读档同行恢复入口。两者都不在配置工作线程中主动生成 NPC。

定位器从公共伴侣查询的直接调用者中寻找控制入口，确认 r8b 为召唤 / 收回标志、r9w 为可操作角色，以及关系键和实例字段。HDE 检查输出仅为 DWORD。再从其原生创建调用恢复所属角色、所属玩家和 ActorId 字段，从注册表查找函数恢复散列表布局。当前入口 RVA 为 0x02b44a60，仅作分析记录，不是定位常量。

控制包装函数在游戏原调用线程中执行：

1. 读取当前角色真实状态 2 集合，并从原生角色注册表核对对象保存键、所属角色及所属玩家。控制组件的 owner 必须就是该服务端注册表中的玩家，不能混用客户端副本。
2. 召唤时优先保留已关联的有效实例，逐个通过原版动作收回同一对象的其他副本；没有实例的对象才允许原版创建。
3. 每次重新查找真实记录，以原子比较替换更新其 DWORD 实例关联，不改对象键或婚姻状态。复用既有实例时仍经过原版控制器与创建包装，返回真实实例 ID，并发送原生召唤回执。
4. 收回时逐个处理已验证实例。原版返回 0 但没有解除关联不能记作完成；异步移除按 ID 和地址标记，实例退出注册表前不再复用或重新创建。
5. 每个对象独立执行原版场景检查。一位失败不会跳过其余对象；主对象结果保留，但不得从返回 0 推断出场已完成。
6. 选择作用域结束恢复，递归不再次扩展。日志将原生结果与实例数、pending / verified 分开记录。

临时对象固定仅适用于已捕获的关系组件和同一角色；组件变化或真实已婚记录不可用时不回退到错误对象。全员扩展可以在提交覆盖关闭时使用，其作用域内选人优先于全局偏好，但不会改变全局偏好。

创建复用在 Enabled 开启且整组原生挂钩就绪时生效；全员处理仍由 SpawnAllPartners 单独控制。不能仅用 extrasAccepted 判断渲染、位置或跟随完成，注册表核验也不能替代这些实机观察。

出场路由使用 thread_local 作用域，插件又静态链接 CRT，因此保留 DLL 线程通知，未调用 DisableThreadLibraryCalls；依据见 [Microsoft API 文档](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-disablethreadlibrarycalls)。

## 读档恢复同行（v0.1.2，待实机验证）

2026-11-02 的 slot108 副本中有三条已婚关系，三条 `_isParty` 都为 true。原版恢复分支却只查询一个当前伴侣，检查该对象保存的同行标志后直接调用创建函数，没有经过已扩展的手动召唤控制器。

新增定位从已验证的原生创建入口反查调用者，排除手动召唤控制器；交叉检查公共伴侣查询、保存标志读取、条件判断、同行参数和 DWORD 输出契约。定位不使用固定 RVA。该入口作为独立可选挂钩安装，失败时仅关闭恢复扩展，保留此前九个原生挂钩和原版恢复。通过 `PartnerRestoreActive` 单独报告是否启用。

恢复包装先取得当前角色已婚键集合。首次执行保留原版/配置选中的对象及调用方结果；其他对象逐一在临时查询作用域中执行同一个原版恢复函数。每次仍由原版读取该对象的 `_isParty`，决定是否创建同行实例，不自行修改存档标志，不把全部已婚对象一律设为同行。每次调用后重新查找记录，不保留跨调用的数组元素指针；递归作用域阻止重复扩展。

创建入口继续使用已有实例复用保护，不盲目复制已存在角色。日志区分已检查对象、原版请求同行、实例复用及错误；这些计数不能替代实际跟随验证。已有实例的 AI 状态、场景切换和连续读档仍需实机验证，本轮仅实现并编译，不宣称这部分已完成实机回归。

## 离婚目标与删除换位保护

游戏包含显式按键和无编号公共离婚两条路径。前者保留原生提供的 NPC 保存键，只在写入前处理该对象的副本。后者先查询当前伴侣，再调用按保存键离婚函数，因此单独绑定已核验的交互对象。

旧入口的目标来自确认交互步骤：请求的两端须恰有一端是当前玩家，另一端是当前角色真实已婚 NPC，支持两端顺序交换。两端都不是玩家的自动交互忽略；重置、结束或无效玩家请求清除目标。预占交互和 SetQuestDialog 缓存填充均不作为已确认目标。旧离婚入口再次核对所属玩家和实例，不用最近结婚、展示偏好或数组第一位代替。

关系数组删除会用末项填补空位，而原离婚入口之后仍从查询结果地址读取字段生成通知。为避免通知另一人，本次离婚单独使用已验证记录的线程局部快照，并固定为实际交互实例 ID。定位器分别审核删除前和成功通知分支对该记录的读取范围，排除失败分支对 R14 的其他用途；不允许写入或越过记录边界。

按键离婚包装先收回同一对象的额外副本，再把实际交互实例留给原版离婚清理。普通收回可能因对话状态拒绝该实例，不能先强制让它走普通收回再决定能否离婚。原版仍负责状态写入、删除和通知；没有可核验交互目标或无法清理副本时停止。

## 兼容性边界

自动定位针对“类型仍存在、RTTI ABI 不变、分派与三态结果模式仍兼容，但地址或槽号移动”的更新，减少手动更新偏移的需要。它不比较游戏版本、PE 时间戳或固定映像大小，也不会通过删除所有检查来强行挂钩。

以下变化仍可能需要维护：类型改名或移除、RTTI 被裁剪、多个候选虚表无法区分、分派代码被改写、异常目录缺失、调用约定或返回语义改变。

## 原始资源与存档研究

本机使用 PAZ / PAMT / PAPGT 资源体系。未发现独立的配偶人数上限参数。当前 PAPGT 是含签名的索引格式，研究选择运行时挂钩，没有修改资源索引。

已定位的条件包括 DLC 条件 1013712、1014823 至 1014826，以及交互表 1000396、1000397、1000378、1000379 中的 HasLivingTogether。条件 1013714 中的 CheckMaritalState(<Me>,Single) 仍保留。

公开存档中存在 FieldNPCMaritialStateSaveData（游戏原名如此拼写），包含 _playableCharacterKey、_maritalState 和 _isParty；FieldNPCSaveData 通过 _npcMaritialStateDataList 保存记录。另有遍历列表、返回第一个符合条件对象的查询。因此解除交互条件并不能保证婚姻写入、同居对象选择、保存重载和离婚支持多对象。
